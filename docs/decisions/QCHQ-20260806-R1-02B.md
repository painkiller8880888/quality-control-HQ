## Scout停止を受けた決定

Issue #23のScoutで、現行文書と実装だけからはSnapshot hash mapping、Catalog三state、State probe、DB timeout／transport schemaを一意に決められないことが確認された。Issue #23の現在の本文および追加decision commentは、推測によるruntime実装を停止し、以下の契約をPhase Aのdocs-only変更として先に確定する決定を採用した。

## Phase Aで確定した契約の要約

- **Snapshot**: 既存`digest()`、`canonical_json_bytes()`およびgolden testをcanonicalizationの正本とする。exact semantic payloadから`semantic_hash`を、public identityとsemantic payloadから`baseline_hash`を算出する。`host_hash`、`port_hash`、時刻、PID、durationなどのvolatile valueは公開結果またはhashへ追加しない。restore OIDがsource OIDと同じ場合はfail-closedとする。
- **Catalog**: `absent`、`existing_empty`、`eligible`の判定表を固定する。複数候補、OID／owner不一致、他connection、欠測、型不正、query失敗、timeoutはstateへ丸めずfail-closedとし、`eligible`は同一executionのCleanup guardに限定する。
- **Restore identity**: `absent`のPlanOnlyでは未来OIDを予測せず`restore.oid_hash = null`とする。`existing_empty`はOIDを必須とし、CreateRestore成功result、作成後Catalog再観測、manifestのendpoint／database／expected ownerが一致したときだけidentityを固定する。Execution evidenceへexact `restore_identity`を保存してmanifest hashへ結び付け、Cleanup approvalは`manifest_sha256`と`execution_sha256`を必須とする。approval、evidence、Catalog identity、connections=0、active Jobs=0が一致した場合だけCleanupを許可する。
- **Jobs**: 全Jobの`status IN ('queued','running')`を数える。`resource_key`、`job_type`、追加の論理削除filterは導入せず、結果は0以上の32-bit整数とする。query失敗、timeout、負数、overflow、collection、型不正はfail-closedとする。
- **State**: manifest echoを観測結果として扱わない。jobsはDB再照会、source／baselineはSnapshot、restoreはCatalog（必要時Snapshot）、clientsはread-only version probe、storageはread-only capacity probe、ownersはcatalog＋固定identity、servicesは`Get-Service`等のread-only probeを正本とする。`running`以外はguardでfail-closedとし、restore absent時のOID nullだけを許可する。serviceのstart／stop／restart、設定変更、process killは行わない。
- **Timeout／injection**: connect 5秒、query 15秒、lock 1秒、helper 60秒の有限timeoutを固定する。無制限を許可せず、connection factory、query runner、clock／timeout source、helper invokerを注入可能とする。read-only providerからDDL／DML、advisory lock取得、service mutationを行わない。
- **Transport**: PowerShell 5.1↔Pythonはstdin／stdoutの単一JSON envelopeとする。`schema_version`、`operation`、`payload`、`timeouts`を持つrequestと、`schema_version`、`success`、`result`、固定reasonを持つresponseのexact shapeを固定する。raw exception、SQL、connection string、host、database、path、stdout／stderrを公開せず、extra／missing field、複数JSON、非JSON、型不正、timeoutはfail-closedとする。

詳細な現行契約は[`specification/RELEASE.md`](../../specification/RELEASE.md)を正本とする。decisionの背景と詳細履歴は[Issue #23](https://github.com/painkiller8880888/quality-control-HQ/issues/23)および[Issue #24](https://github.com/painkiller8880888/quality-control-HQ/issues/24)に記録する。`docs/history/`は凍結履歴であり、今回変更しない。

## 作成前OID要求の撤回

復元先が`absent`の場合に、作成前のOID hashをPlanOnly manifestへ要求する旧契約は撤回する。PostgreSQLのOIDは作成時に割り当てられるため、PlanOnlyでは`restore.oid_hash = null`を記録し、CreateRestore後のCatalog再観測で実OIDとownerを固定する。

## Phase Bの扱い

Phase Bのvalidator、provider、fake/static testおよびruntime実装は、このPhase Aの仕様PRがレビュー・マージされるまでblockedとする。Phase Bでは、マージ済みの[`specification/RELEASE.md`](../../specification/RELEASE.md)を正本として再Scoutを行う。

## 変更しない境界

このdecisionは`LIVE_BLOCKED=True`を変更せず、criterion 8も変更しない。Issue #23で確定したCleanup approval contractの変更（`manifest_sha256`と`execution_sha256`の両方を必須とすること）を記録する。それを超える追加のsecurity policyまたはapproval policyは導入しない。Issue #23で確定したread-only境界、privacy-safe result、既存のlive-blocked条件は維持する。runtime、validator、test、adapter、production auto-wiring、実DB／network／UNC／service、`pg_dump`／`pg_restore`は本decisionの対象外である。
