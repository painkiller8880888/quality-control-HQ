# Sol–Luna Codex 開発パイプライン（個人開発版）

> 元の「Sol–Luna Codex開発パイプライン運用忘備録」から、個人開発に必要な骨子だけを抜き出した版である。
> チーム運用や契約的な品質保証を前提にした仕組み（役割の二重化、状態ラベル管理、大量の証跡テンプレート、導入フェーズ、運用指標など）は省略した。省略した項目は末尾（10章）にまとめてある。
> RP・調査・Plan・PR・AGENTS.mdの各テンプレート定義は行数の都合で `schema.md` に分離した。

---

## 0. tl;dr

このパイプラインの核は「判断」と「実装」を分けることにある。

- **Sol Chat**（Web版の強力なモデル）が、要求の整理・実装計画・モデル選定・PRレビューを担当する。
- **Codexコーディングエージェント**が、実際のリポジトリ操作（実装・テスト・PR作成）を担当する。原則として安価なモデル（Luna）を使い、必要な場合だけTerra、さらにSol Codexへ昇格する。

```text
Issue作成（RP）
  ↓
Sol Chatによる計画・難易度判定
  ↓
Codex（Luna）による実装・検証
  ↓
Draft PR作成
  ↓
Sol Chatによる独立レビュー
  ↓
Codexによる修正
  ↓
CIと自己確認
  ↓
マージ
```

Lunaで解決できない場合は、次の順で昇格する。段階を飛ばして直接Sol Codexを使わない。

```text
Luna → Terra → Sol Codex
```

Sol Chatは実環境を直接操作できないため、Codex側には「何をしたか・何を確認したか・何を確認できなかったか」をPR本文へ書かせる。これが正式な記録になる。

---

## 1. なぜこの分担にするか

目的は最も高性能なモデルを常に使うことではなく、**モデルを最も価値の高い工程へ割り当てる**ことである（得意・不得意の内訳は次章の表を参照）。Sol系のモデルをCodex上で常時使わないことがコスト削減の核心であり、これを崩さないことが最重要である。

---

## 2. 役割分担

| 役割 | 担当すること | やらないこと |
|---|---|---|
| 自分（人間） | 要求の承認、最終判断、マージ | AIの自己申告だけで採用する |
| Sol Chat | 計画、モデル選定、独立レビュー | 実環境を見たつもりになる／大量の実装コードを書く |
| Luna | 調査、実装、テスト、PR作成 | 不明点を推測で埋める |
| Terra | 中難度の実装、Lunaの検証、統合作業 | 必要以上に変更範囲を広げる |
| Sol Codex | 最高難度の実装・デバッグ | 通常作業への常用 |
| GitHub | 状態・差分・レビューの正本 | チャットだけに情報を残す |

会話（ChatGPT・Codexとのやり取り）は作業の場であって正式な記録ではない。判断・実装・検証結果は必ずGitHub（Issue／PR／commit）へ残す。

---

## 3. 標準フロー

Sol Chatはリポジトリの実態を直接見られない。計画がSol Chatの思い込みの上に立たないよう、**計画を確定する前に必ず読み取り専用の調査を挟む**。

```text
1. RP（要求）をIssueとして書く
2. Sol Chatがまず読み、調査すべき不確実性を洗い出す
3. Luna（必要ならTerra）が読み取り専用で調査し、
   結果（関連ファイル・現状の実装・依存関係・既存テストの状態など）を返す
4. Sol Chatが調査結果をもとにPlanとモデル（原則Luna）を確定する
5. CodexのworktreeでLunaに実装させる
6. 検証スクリプトを実行させる
7. Draft PRを作らせる
8. Sol ChatにPRを独立レビューさせる
9. 指摘をLunaに修正させる
10. CIを通す
11. 自分で最終確認してマージする
```

調査役（2〜3番）にはコードを変更させない。調査結果はschema.mdのテンプレート程度で十分で、厚くしすぎるとこのステップ自体が形骸化する。省略していいのは「typo修正」のように1ファイルで完結し自分でtrivialと言い切れるタスクだけとし、迷ったら省略せず実行する（Lunaでの調査は安価なので"迷ったらやる"側に倒してよい）。

---

## 4. 昇格ルール（コスト管理の核心）

Lunaは同じ問題に無制限に再試行させない。次のいずれかに該当したら、その場で作業を止めて昇格する。

**Luna → Terra**
```text
変更対象が当初予定の2倍以上に広がった
複数の責任領域（フロント／API／DBなど）をまたぐ
既存テストが理由不明で失敗する
2回修正しても受入条件を満たせない
実装方式が複数あり、局所判断で選べない
```

**Terra → Sol Codex**
```text
根本原因を特定できない
認証・権限・セキュリティに関わる
破壊的なDBマイグレーションが必要
並行処理・競合状態が絡む
影響範囲を限定できない
```

昇格するときは、次を短くPRやIssueコメントへ書き残す。試したこと・確認できた事実・未解決点・推奨する次のモデル、これだけで十分である。モデルの切り替え自体は`codex --profile terra`／`codex --profile sol`のようにprofileで行う（定義はschema.md参照）。

## 5. 最小リポジトリ構成

```text
/
├─ AGENTS.md
├─ .github/
│  └─ PULL_REQUEST_TEMPLATE.md
├─ specification/
│  └─ ai/
│     └─ schema.md
└─ scripts/
   └─ verify.sh（Windowsならverify.ps1）
```

テンプレート定義（RP・調査・Plan・PR・AGENTS.md）は`docs/ai/schema.md`にまとめる。`architecture.md`や`review-rubric.md`のような追加ファイルは、必要になるまで作らなくてよい。

---

## 6. 検証スクリプトの原則

検証コマンドをその都度モデルに選ばせず、`scripts/verify.sh`に固定する。Codexも自分もCIも同じ入口を使うことで、「手元で通った」と「CIで通った」がずれなくなる。

```bash
set -e
pytest
ruff check .
npm run lint
npm run build
```

プロジェクトに存在しないコマンドは削除し、実際に使うものだけを残す。

## 7. モデル選定の目安

**Lunaでよい作業**：CRUD追加、フォーム修正、既存パターンに沿った画面追加、単体テスト追加、型・lintエラー修正、文書更新、限定的なリファクタリング、レビュー指摘への対応。

**Terraを検討する作業**：複数モジュール・複数層をまたぐ変更、既存設計の読み解きが必要、実装案が複数あり比較が必要、Lunaが一度失敗した。

**Sol Codexだけに任せる作業**：認証・権限・セキュリティ、破壊的マイグレーション、並行処理・競合状態、原因が複数層にまたがる障害、LunaとTerraがともに失敗した問題。

## 8. Handoffログの方針

GitHubに残る成果物（RP・Plan・diff・PR）は実装の正本だが、そこには「どこで軌道修正が起きたか」という試行錯誤の過程は残らない。フローやプロンプトの改善を目的に、生のやり取りを別途ログしておく価値がある。ただし全部残すと保存・整理の負荷がノイズに埋もれて勝つので、範囲を絞る。

```text
Sol Chatとの計画・レビュー会話 → 残す（量が少なく、改善の手がかりが濃い）
Codex（Luna/Terra）の実行ログ  → 昇格（4章）が起きた回だけ残す
```

保存先はリポジトリの外に置く。secretや実装の中身が無意識に混ざりやすく、AGENTS.mdの「secretを含めない」というルールと衝突しやすいため。

見返すタイミングを先に決めておく（昇格が起きるたび、月1回まとめて、など）。ログを取ること自体には価値がなく、読み返してAGENTS.md・受入条件・昇格条件を更新して初めて意味が出る。

## 9. 一回分の流れ（例）

```text
自分:      Issue #12としてRPを作成する
Sol Chat:  RPを読み、調査すべき不確実性を挙げる
Luna:      読み取り専用で調査し、結果を返す（schema.md参照）
Sol Chat:  調査結果をもとにPlanを確定する
Luna:      codex/12-feature-name で実装、verify.shを実行、Draft PR作成
Sol Chat:  RP・diff・検証結果を照合し、指摘を出す
Luna:      指摘を修正、検証を再実行
CI:        自動チェックを実行
自分:      検証結果とレビューを確認してマージする
```

## 10. 個人開発向けに省略したもの

元文書には次の仕組みもあるが、チーム運用や高い保証を前提にしたものなので、個人開発では省略している。必要になれば個別に追加すればよい。

```text
Planning ProjectとReview Projectの分離（自分一人なら一つのプロジェクトで十分）
Codex側Verifierによる独立検証（自分の確認で代替する）
12種類の状態ラベルとその遷移管理
Evidence Packetの詳細項目（DB状態、印刷キュー、実行ユーザーなど）
Windows・Excel COM・社内LAN固有の運用ルール
導入ロードマップ（Phase 1〜4）
運用指標10種の計測
Sol Chat／Codex Worker／Verifier／CI／人間の責任分界の明文化
開始時チェックリスト
```

---

## 11. 最終原則

品質は一つのモデルの性能では作れない。明確なRP、実行可能なPlan、限定されたdiff、再現可能な検証、独立レビュー、CI、そして自分の最終判断の組み合わせで作る。

このパイプラインで重要なのは、Sol Codexを一度も使わないことではなく、**Sol Codexを使うべき問題と使わなくてよい問題を正しく分けること**である。
