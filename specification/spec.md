# 日報アプリ仕様書

## 0. 現行実装同期（2026-07-15）

この節は現行コードを根拠とし、旧記述と矛盾する場合はこちらを優先する。

- DB は PostgreSQL、OCR は RapidOCR、フロントエンドは React/Vite、API は Django REST Framework である。
- 全業務 API はセッション認証を既定とする。利用者は `admin` と `worker` の2ロールで、管理設定、ERP更新、マスタ・機械・クラス9設定、検査サマリー等は `admin` 限定である。
- 検査セッションは利用者ごと・対象日ごとに分離され、一意キーは `(owner_user, target_date)`。対象・履歴も作成者のスコープで取得・更新される。
- 対象一意キーは `(session, normalized_code, class_override)`、履歴一意キーは `(created_by, date, master, time_slot, class_override)`。いずれも `NULL` を同値として扱う。
- 通常の検査書対象はクラス 1/6/7。明示的に登録されたクラス9は常に検査書対象である。
- 見取り図は複数レイアウト、機械割当、種別色変更を実装済み。背景画像の保存・配信は未実装である。
- `Job` レコードとポーリング APIはPostgreSQL上の永続キューを使用する。APIは処理を待たずにqueued Jobの`job_id`と202を返し、専用workerが`select_for_update(skip_locked=True)`、resource単位の排他、依存Job待機、idempotency key、heartbeat／lease回収、承認済みretryで処理する。

正式リリース要件、優先度、受入基準の正本は `RELEASE.md` とする。実施結果や進捗はGitHubのIssue／PR／commitを参照する。

## 1. 目的
- 工場内の巡回検査業務をデジタル化し、検査対象の把握、検査実績の記録、検査書発行、日報出力を一元管理する。
- 当日の検査対象を「後から再現できる状態」で保存し、日報や履歴の整合性を担保する。
- 将来的なERP連携、自動化、オンプレミス運用に耐えられる構成で段階的に実装する。

## 2. 対象機能
- ERP由来の品目マスタ、構成、検査書ファイル情報の更新
- 作業計画PDFのOCR取込
- 作業計画Excelの取込
- 手動での検査対象追加
- 当日検査対象リストの作成と保持
- 検査チェックの記録
- 見取り図による巡回ガイド表示
- 検査書の個別発行、一括発行
- 日報Excelの生成
- 検査履歴の保存と再表示

## 3. 技術構成
- フロントエンド: React
- API: Django REST Framework
- バックエンド: Django / Python
- データベース: PostgreSQL
- ツールチップ: Reactコンポーネント、CSS、ブラウザ標準 `title` を用途に応じて使用
- OCR: RapidOCR
- ERP操作: pywinauto

## 4. 業務上の主要概念

### 4.1 検査セッション
- ログイン利用者ごと・対象日ごとに1つの `inspection_session` を持つ。一意キーは `(owner_user, target_date)` とする。
- 当日の検査対象、警告、発行状態、チェック状態はこのセッションに紐づけて保存する。
- 同じ日付で再取込した場合も、同一セッションを更新する。

### 4.2 検査対象
- 当日の検査対象は `inspection_target` として保持する。
- 1レコードは「その日、その品目が検査対象である」ことを表す。
- OCR、Excel、手動追加の複数ソースを統合して重複排除する。

### 4.3 チェック時間帯
- チェック時間帯は固定マスタとする。
- `A = 08:30-10:00`
- `B = 10:10-12:00`
- `C = 12:45-14:45`
- `D = 15:00-17:15`
- MVPではこの時間帯定義を変更しない。

### 4.4 検査書発行状態
- 検査書発行状態は以下を持つ。
- `not_required`: 発行不要
- `pending`: 発行対象だが未発行
- `issued`: 発行済
- `missing_file`: 発行対象だがファイル未発見
- `skipped`: 利用者判断またはシステム判断で今回未発行

## 5. パイプライン

### 5.1 ERPマスタ更新
- UIから実行指示を受ける。
- バックエンドがWindows上でERP自動操作を行い、CSVを取得する。
- 現行更新は単一DB transaction内で、Master/MasterClass/Structureを `update_or_create` し、InspectionFileを全削除後に走査結果から再作成する。
- 処理中に例外が発生した場合はtransaction全体をrollbackする。`staging -> validation -> swap` は未実装であり、採用判断と受入基準は `RELEASE.md` の将来要件とする。
- 検査書フォルダ走査結果の再作成も同一transactionに含む。
- 走査対象フォルダには整数の優先順位を設定でき、走査時は各候補へ優先順位と取得可能なファイル作成日時を記録する。候補自体は優先順位や日時にかかわらず全件保持する。
- 同一品番・同一classの検査書が複数ある場合、優先順位が高いもの、同順位なら作成日時が新しいものを表示・PDF・印刷・一括発行で共通選択する。日時なしは日時ありより後とし、完全同値時は正規化パスとIDで決定する。異なるclass間の矛盾とclass 9の専用設定は従来どおり扱う。

### 5.2 作業計画取込
- OCR対象PDF、計画Excel、手動追加を受け付ける。
- 取り込み結果はログイン利用者本人の同一対象日の `inspection_session` に集約する。
- コードはユニーク化して `inspection_target` に保存する。
- 未登録コード、OCR失敗、重複などは警告として記録し、UI表示可能にする。
- 作業計画は見取り図から機械を指定して登録、あるいは品目コードの入力による手動追加に対応する。

### 5.3 検査チェック
- UI上で検査対象ごとに A〜D の4つの固定チェック枠を表示する。
- チェック状態は `checked / unchecked` の二値とする。
- 対象外はチェック状態ではなく、検査対象から除外することで表現する。
- チェック更新は即時保存する。
- UI上で特定の品目の計画を削除することが出来る。これはUI上で非表示にするだけで、実際には `inspection_target` からは削除されない。

### 5.4 検査ガイド
- 当日の `inspection_target` と機械割当を照合し、見取り図上で巡回対象機械を強調表示する。
- MVPでは `rectangle` のみを描画対象とする。
- ツールチップには機械名、担当コード、当日対象コード数を表示する。

### 5.5 検査書発行
- 発行対象はカテゴリ `1` と `6` と `7` のみとする。
- 一括発行は `pending` 状態のみを対象にする。
- 個別発行は状態にかかわらず再実行可能とする。
- 印刷指示は時間帯（A〜D）を指定して行われる。
- Excelマクロは既存資産を利用し、ファイルパスや指示時刻等を引数として呼び出す。
- 発行結果（印刷完了）は、該当する日付・品目・時間帯の `history` レコードにおける `is_sheet_issued` フラグ（印刷済み記録）に反映する。詳細なフローは `sheet_issue_spec.md` を参照。

### 5.6 日報生成
- 日報生成前に当日チェック状態はDBへ保存済みであることを前提とする。
- 日報生成APIは保存済みデータを所定Excelフォーマットへ転記する。
- 同日に対する再実行では、常にその時点の最新状態で上書き生成する。
- Excel出力失敗時でも、保存済みの検査状態は失わない。

### 5.7 見取り図作成
 - UI上で見取り図をグリッドベースで作成・編集可能とする。
 - 機械、通路、エリアをドラッグ操作で配置し、レイアウト情報をDBへ保存する。
 - 背景画像は現行未実装であり、保存・表示しない。
 - 保存済みレイアウトは検査ガイド画面から参照可能とする。

## 6. 状態管理方針

### 6.1 当日データの保持
- 当日検査対象、警告、検査書発行状態は履歴として保存し、再生成時も参照可能にする。
- `history` は「いつ、どの品目が、どの時間帯で検査済になったか」を表す。
- 当日対象そのものは `history` ではなく `inspection_target` で保持する。

### 6.2 冪等性
- 検査チェック更新は同じ入力に対して何度実行しても同じ状態になるようにする。
- 日報生成は同一日付に対して再実行可能とする。
- 一括発行は `pending` だけを対象にすることで重複発行を抑制する。

## 7. 現行ジョブ方針
- ERP更新、OCR取込、検査書一括発行、日報生成は、PostgreSQLの永続Jobキューへ登録する。
- APIは処理完了を待たず、`queued` Jobの`job_id`と202を返す。ジョブは `queued / running / succeeded / failed` の状態を持つ。
- 専用workerはtransaction内の`select_for_update(skip_locked=True)`でJobをclaimし、resource単位のadvisory lock、依存Jobの完了待機、worker ID、heartbeat、lease、attempt count、execution tokenを管理する。
- 同一resourceとidempotency keyの重複要求を集約し、lease失効時はJob種別に応じて承認済みretryまたは安全な失敗とする。旧workerの重複配送が復旧後の試行を上書きしないことを保証する。

## 8. MVPスコープ
- 手動追加、Excel取込、検査対象一覧、A〜Dチェック保存、履歴再表示、日報出力
- 見取り図表示はMVPに含めるが、図形は `circle / ellipse / rectangle` のみ
- ERP自動更新、OCR、検査書一括発行はMVP後半または次フェーズでもよい

## 11. 検査サマリー・検査ノート（2026-07-14）

- 管理者は、指定月または任意の日付範囲について、クラス別検査回数、上位10品目、日別推移、日別・検査者別内訳を確認できる。
- 検査回数は未削除の `quality_history` 1レコードを1回とし、`class_override` を優先、未指定時は品目の検査クラスを使う。期間は両端を含み、0件の日も表示・出力する。
- 検査者は日付ごとに自分の検査セッションへノートを保存できる。セッションがなければ保存時に作成し、closed状態でも更新できる。
- 集計CSVとノートCSVはUTF-8 BOM付きで、ブラウザのフォルダ選択APIが利用できない場合は通常ダウンロードへフォールバックする。
